# Create Plan

1. Discuss First (default) - For a new plan, invoke the sibling **`discuss`** skill's Interview workflow before authoring anything, **unless the requester explicitly says to skip it**. Depth scales with stakes per its rubric: a short pass (goal, stack fit, edge cases) for small features; the full relentless interview for new systems or architectural changes. Its resolved decisions arrive as **locked inputs** — capture them faithfully in the plan (including inline links to any ADRs it recorded) and do not relitigate them.
2. Analyze Requirements - THINK HARD and parse the `USER_PROMPT` (plus any locked inputs from the discuss pass) to understand the core problem and desired outcome
3. Explore Codebase - Understand existing patterns, architecture, relevant files, and prior specs to back-reference. If present, read the context artifacts (`STACK.md`, `CONTEXT.md`, `SYSTEM.md`, `docs/adr/` — see `## Context Layer` in SKILL.md), and read `AI_DOCS` for AI/agent-facing documentation and `APP_DOCS` for application documentation to ground the plan (skip silently when a project doesn't have them).
4. Design Solution - Develop technical approach including architecture decisions and implementation strategy
5. Name the Plan - Choose a descriptive kebab-case slug for the plan's main topic. It becomes the filename (`specs/<kebab-name>.html`) and the immutable `id`.
6. Scaffold - Run `PLAN_TOOL new <kebab-name> --title "<Plan Title>" [--owner <role>]` to stamp a fresh `specs/<kebab-name>.html` from `templates/plan.html`: it fills every `data-*` anchor and the metadata (`id`, `created`, `modified`, `status=draft`, `schema`) and lays down one example phase (`phase-1`, tasks `1.1`/`1.2`) plus one global check (`g.1`) for you to duplicate. `new` refuses to overwrite an existing plan and logs a `created` event — no `init-ids` needed.
7. Author Visual Identity - The template ships **unstyled**: author the single `<style>` block in `<head>` yourself, with a `:root` custom-property palette (bg/surface/border/text/accents) themed to the `USER_PROMPT`. This palette is the plan's synced visual identity — the diagrams reuse its hex values. Style every structure the template and your content use (header, metadata `details.meta`, sections, figures, code/pre, checklists, `.tag`/`.status`, `.phase`, `.loop`, tables). An existing plan in `specs/` is a good quality bar.
8. Author Content - Edit the scaffold **in place** (it already exists, so author with Edit, not a full-file Write). Add the phases the plan needs with `PLAN_TOOL addphase PLAN_FILE --tasks <N> --title "<phase name>"` — it appends a correctly-numbered block (`data-phase`, `data-task`, `data-status-for`, Testing Strategy) so you never hand-author structural HTML. Then replace every `{{...}}` content slot (purpose, problem, solution, file paths, phase names, task names, actions, testing approach, notes, figure subjects) with real content. Duplicating a checklist item or an extra global check (`g.2`, …) by hand is allowed by the guard **only while the plan is `draft`** (the draft authoring window — see `## Managed Writes`); never hand-edit the metadata or amendments, and never flip a status marker by hand in any state.
9. Generate Diagrams - Run the Create sub-workflow in `workflows/diagram-generation.md` to fill the `{{...IMAGE` slots with Excalidraw diagrams. Author the diagrams one at a time (the render step is fast and local). If the `excalidraw-diagram` skill is not installed, degrade gracefully: replace each `{{...IMAGE: subject}}` placeholder with a **plain comment naming the subject but with the `{{ }}` braces stripped** (e.g. `<!-- diagram TODO: the flip at a glance -->`), and keep the authored `<figcaption>`. Stripping the braces is what lets the plan leave `draft` later — a leftover `{{...}}` token is a validation *warning* in `draft` but a *failure* outside it, and `PLAN_TOOL meta … --field status` now refuses to move a plan off `draft` while any `{{}}` slot remains. Tell the user diagrams are still pending and can be generated once the skill is installed.
10. Surface Open Questions - Keep the Open Questions section (`QUESTIONABLE` defaults true) and populate it with the open decisions, assumptions, and risks this plan carries — every judgment call you made without confirmation belongs there, one `<details>` each, with the assumption or rationale you proceeded on. A plan with no open questions is rare; if the plan genuinely has none, say so in one line rather than leaving `{{}}` slots. Delete the section only when the `USER_PROMPT` explicitly asks for no open questions
11. Validate - Run `PLAN_TOOL validate PLAN_FILE` and fix any failures. While the plan is `draft`, unfilled `{{}}` slots report a placeholder *warning* (not a failure) — but replace every slot before the plan leaves `draft`.
12. Index - Run `PLAN_TOOL index` to refresh `specs/_index.json` / `specs/_index.html` and surface any dangling references or doc drift
13. Register - If `STATE_FILE` exists, run the `workflows/sync-state.md` subworkflow to register the plan under In Development and append the ledger entry. If it doesn't and the user wants state tracking, mention that Init State is available and move on.
14. Open in Browser - Open the saved plan in the default browser using the platform-appropriate command: Windows `start "" PLAN_FILE`, macOS `open PLAN_FILE`, Linux `xdg-open PLAN_FILE`
15. Report - Provide a summary of the plan's key components
