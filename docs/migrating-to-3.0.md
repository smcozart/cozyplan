# Migrating from 2.x to 3.0

3.0 changes who owns two things: **work items** move from files to your issue tracker, and **`STATE.md`** moves from authored to generated. Nothing in your repo is deleted by upgrading — cozyplan simply stops maintaining what it no longer owns — but two of these need a deliberate step from you.

## What changed

| | 2.x | 3.0 |
| --- | --- | --- |
| Features and bugs | `docs/features/FEAT-NNN-*.md`, `docs/issues/ISSUE-NNN-*.md` | GitHub issues via `gh`, per `docs/agents/issue-tracker.md` (ADR-0001) |
| `STATE.md` | Authored by hand, sections overwritten on sync | Generated by `plan_tool state render` from `docs/state.ndjson` (ADR-0005) |
| Templates | `templates/feature.md`, `templates/issue.md`, `templates/STATE.md` | All three removed |
| Wiring a repo | A manual checklist | `plan_tool init` |
| Ownership maps | `plan_tool roles build` → `roles/_roles.json` + `.github/CODEOWNERS` | Removed; write `.github/CODEOWNERS` directly (ADR-0009) |
| `STATE.md` length | Capped at 20 per section, ranked by a `weight` field | Uncapped; ordered by commit position (ADR-0008) |
| Trailer injection | — | Tracked `.githooks/` + `core.hooksPath` (ADR-0007) |

## Upgrading

**1. Wire the repo.**

```bash
plan_tool init
```

Idempotent: it creates only what is missing and never overwrites content you wrote. The two exceptions are the tracked `.githooks/` scripts and the Claude hook registration, which it rewrites every run so they re-point at a moved interpreter; its report lists those under **refreshed**. Read the report — anything under **needs a human** is a step no command can take (branch protection, `gh` auth, the origin remote, git identity).

**2. Carry your `STATE.md` into the event log.**

`state render` **refuses** to overwrite a `STATE.md` that it did not generate, so an accidental upgrade cannot destroy your snapshot. To adopt it deliberately:

```bash
plan_tool state migrate     # --dry-run first, to see the events it would append
plan_tool state render
```

`migrate` carries your claims (with their original dates and any commit anchors), your In Development rows, and your gaps. It **cannot** carry:

- **`paths`** — no source in the old format. The path-intersection sync trigger cannot fire for migrated claims until you add them.
- **`sha` on date-only claims** — deliberately left absent. Back-filling it to `HEAD` would assert a proof ran at a commit where it never ran.
- **The `## How to Run / Verify` block** — it has no event kind and no rendered section. Copy it into `CLAUDE.md` or your README.
- **The `Synced by` identity** — the schema has no email field.

`migrate` prints every one of these, and keeps your original at `STATE.md.pre-migration`. Salvage what it names, then delete the backup.

**3. If you used `plan_tool roles build`, take over `CODEOWNERS` by hand.**

The command is gone. Your existing `.github/CODEOWNERS` still works and git still reads it; nothing regenerates it now. `roles/*.md` and `roles/_roles.json` are no longer read by anything, so keep them as notes or delete them. The plan `owner` field is unaffected.

**4. Decide what to do with `docs/features/` and `docs/issues/`.**

Cozyplan no longer reads or writes them. They are still in your repo and still valid markdown. Either file the open ones as issues (`gh issue create`) and delete the directories, or leave them as a historical record — nothing breaks either way. Anything still open is better off where it has a queue, an assignee, and a notification.

## If you would rather not migrate

Pin to 2.2.0. The state layer in 3.0 is not backward compatible with an authored `STATE.md`, and the guard exists so that staying on the old shape fails loudly rather than silently.
