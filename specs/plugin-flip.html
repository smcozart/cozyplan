Purpose

Migrate planf3 from a project-local Claude Code Agent Skill (plus a hand-merged hook config) into a single distributable Claude Code plugin: skill, slash commands, deterministic CLI, and enforcement hooks all arrive together via /plugin install planf3, update centrally via /plugin update, and operate on any project's specs/ unchanged. This plan is authored from the existing packaging design (plugin-path-design.md) and covers the mechanical flip only — execution is deliberately deferred until a flip trigger fires (see Notes).

Problem

Installing planf3 into a project today takes three manual steps, and the worst one is blocked for agents: copy .claude/skills/planf3 into the project, copy scripts/, then hand-merge .claude/settings.json.sample into the live settings.json — agents are permission-blocked from writing live settings, and humans get the merge subtly wrong. Because the machinery is copied per project, there is no central update path: fixes to plan_tool.py or the hooks drift across projects, a team cannot converge on one version, and a hand-copied skill sitting beside a newer copy can double-trigger or diverge. The root cause is that machinery (versioned tooling) and artifacts (each project's living plans) are tangled in one tree.

Solution

One load-bearing split drives everything: machinery ships in the plugin; artifacts stay project-local. This repo becomes the plugin repo — a .claude-plugin/plugin.json manifest, skills/planf3/ (moved verbatim), commands/ holding three thin wrappers (/planf3:role, /planf3:rollup, /planf3:index), hooks/hooks.json wiring the existing guard/lint scripts via ${CLAUDE_PLUGIN_ROOT}, and scripts/ exactly where it already sits. Hooks install with the plugin, so the settings-merge step disappears entirely. Every artifact — specs/*.html, image dirs, *.log.ndjson, specs/_index.*, roles/ — stays in each project's repo, resolved from the project root. The planning flow itself stays a skill (model-invoked, description-triggered); only deterministic operations become commands.

The seams that make this flip mechanical are already landed on main: plan_tool.py is path-agnostic (every command takes explicit paths), both hook scripts and the CLI's template lookup already resolve via CLAUDE_PLUGIN_ROOT with a cwd/scripts fallback (which also preserves the standalone / non-Claude mode), and every plan carries a write-once schema stamp decoupling artifact structure from plugin version. Net result: the flip requires zero Python changes — it is moves, small JSON files, three command wrappers, and a verification pass.

Notes

⏸ Do not execute this plan until a flip trigger fires. The flip is deliberately deferred; until one of these is true, project-local files plus the settings sample is "what works":
  • (a) Role pilot proven — the role system works project-local and iteration on it is done;
  • (b) First teammate — the moment manual install actually costs something;
  • (c) 3+ projects — central-update value materializes.

Why this plan is thinner than the original design

The packaging design (plugin-path-design.md, §2) budgeted one code change: patching both hook scripts to resolve plan_tool.py via CLAUDE_PLUGIN_ROOT. That seam — plus the CLI's own template lookup and the write-once schema stamp — already landed on main (Tier 1 operating layer). The flip is now zero Python changes: moves, three JSON/markdown surfaces, docs, and verification.

Versioning — three deliberately decoupled axes

  • Artifact schema stamp (landed): every plan declares its structural contract (schema=1, write-once). The artifact never depends on the plugin version.
  • Plugin SemVer in plugin.json: the CLI refuses to write a plan stamped newer than it understands ("this plan needs a newer planf3 — /plugin update"), so an old tool never corrupts a newer artifact.
  • Migrations are additive and idempotent: init-ids (which retrofits anchors onto legacy plans) is the precedent; a future plan_tool migrate generalizes it to ordered N→N+1 transforms. A MAJOR bump may raise the minimum schema but must ship a migration at least one schema back. Not part of this flip — future work.

Longevity backstop — protect it

The plan HTML is self-contained (all CSS inline) and renders in any browser with no plugin at all; the machinery is needed only for structured writes, never for reading. Even if planf3 is abandoned someday, every plan remains a readable, self-describing document. Rule: never move rendering or state into external files the plugin owns.

Non-Claude harness degradation (keeps the README honest)

Breaks under pluginization: plugin.json/marketplace, hooks.json, slash commands. Survives anywhere: SKILL.md + workflows are plain markdown instructions, and plan_tool.py is a plain uv/Python CLI taking explicit paths that self-validates on every op — enforcement hooks are a safety net, not a correctness requirement. Two cheap rules preserve this: keep the CLI invocable with explicit paths, and keep the CLAUDE_PLUGIN_ROOT-absent fallback in the hook scripts (both already true).
