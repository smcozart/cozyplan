Purpose

Re-scope planf3 so it keeps every promise it makes. A five-run effectiveness campaign (two solo lifecycles, two guard red-teams, one full roles lifecycle, plus an accidental concurrency test) found a clean split: the authoring core and the coherence/visibility layer are strong and load-bearing, while the compliance-flavored machinery presents as enforcement but degrades to theater under the exact concurrency and multi-agent conditions it targets. This plan does not add features — it re-labels, re-defaults, and fixes-or-drops claims so the tool's behavior matches its documentation. It is the deliberate answer to the owner's question, "is this doing too much?": yes, and here is the honest smaller shape. Planning only — no execution until reviewed and approved.

Problem

The tagline is "coherence, not compliance," yet it is precisely the compliance machinery that fails under real use, while the coherence parts survive. Concretely, five independent runs showed:

  • The integrity guard is defeatable by a determined agent and status-independent: two red-teams independently reached the same two root causes — it matches on token substrings of edit strings rather than on document regions (so value-only edits, MultiEdit token-splits, and edits inside the amendments block all pass), and it matches on raw path strings rather than the normalized file the OS opens (so on Windows a capitalized SPECS/ or a trailing dot walks past both the integrity and role checks). It also can't see Bash writes at all.
  • Protect-mode role denial never fires under multi-agent-in-one-session — the guard reads PLANF3_ROLE from the hook process (the session), not the acting agent's subshell — so live enforcement only works if you launch one session per role, the opposite of the multi-agent story it sells.
  • The "verified" checkpoint doesn't bind a plan to its own work. Under concurrency, build-meta captured a foreign housekeeping commit as a plan's verified HEAD; the check only proves the tree is clean, not that this plan's diff is in that commit. Two agents built the same feature, both marked built + checkpoint-tagged, and index reported "clean, no drift."
  • The acceptance queue, change-requests, and drift duplicate what CODEOWNERS + PR review + git blame already give a small team, while adding an index→rollup→commit choreography with stale-index and dirty-tree foot-guns.

The danger isn't that these features exist — it's that they present as guarantees they don't keep, which is worse than not offering them, because a user relies on a revert point or a role boundary that isn't really there.

Solution

Three moves, in priority order. None removes working code the owner may want at the "3+ projects / real team" trigger — the compliance features are demoted to off-by-default opt-in and re-labeled as visibility, not deleted, which is reversible and cheap.

  1. Fix or drop the checkpoint "verified" claim (correctness first). This is the one that undermines a stated pillar — revertible checkpoints. Either bind a checkpoint to a commit that actually contains the plan's own changes, or stop calling it "verified" and present it honestly as an annotated tag over the current HEAD.
  2. Re-label the guard as a coherence/lint layer, and make the two cheap real fixes. A hook can never be tamper-proof (the Bash gap alone guarantees that), so the only honest framing is "keeps an honest agent honest." Normalize paths with Path.resolve() before matching (kills the Windows case / trailing-dot bypasses) and lower-case role-glob matching — cheap wins that make it keep that honest promise. Do not invest in making it a security boundary.
  3. Demote the compliance machinery to opt-in visibility. Flip protect-enforcement, the acceptance queue, change-requests, and PLANF3_ROLE-based drift to off-by-default, and re-document them as "makes incoherence visible in rollup," not "blocks." Keep the two clear wins always-on: the managed-region integrity guard (now honestly labeled) and roles→CODEOWNERS generation.

Why not revert to 0e63679

The simpler era predates two keepers — the integrity guard and roles→CODEOWNERS — both of which the campaign validated as real wins. A wholesale revert throws those away to escape machinery that a re-scope can neutralize far more cheaply by changing defaults and language. The problem was never that the operating layer exists; it's that it was sold as enforcement it can't deliver in-process. Re-scoping fixes the mismatch; reverting overcorrects.

Guiding principle for execution

Every change in this plan reduces to one test: does the documentation now describe what the code actually does? If a phase can't make a claim true cheaply (checkpoint verification, guard tamper-proofing), it drops the claim rather than faking it. "Coherence, not compliance" becomes literally true: the tool makes incoherence visible and steers cooperative writers; it does not pretend to force anything it can't.

Deferred / out of scope

  • The plugin flip (specs/plugin-flip.html) is independent and still gated behind its own triggers; this re-scope should land first so the plugin ships the honest tool.
  • The amendment-region mutability and new-file-poisoning findings (red-team F3/F5) are accepted as inherent to a cooperative-coherence layer once the guard is honestly re-labeled — worth a one-line "known, by design" note, not a fix.
  • MultiEdit token-split (F4b) — same disposition; a lint layer doesn't need to defeat a determined adversary.
