Purpose

Make planf3's plan authoring context-aware. Two additions, both pure markdown authoring — zero changes to plan_tool.py, the hooks, or the tests: (1) a Discuss Plan workflow — a self-contained, depth-scaled interview that runs by default before a new plan is authored, capturing decisions as ADRs, vocabulary as a glossary, and stack deviations in place; (2) a stack-context layer — a per-repo STACK.md of technology defaults written as default + when-to-use lane + escape hatch, seeded from a generic template, an org seed, or a first-run interview. The goal is cultural, not mechanical: engineers (and agents) slow down, interrogate the idea, and own their process — and the "why" survives in living artifacts instead of evaporating into chat history.

Problem

Today the Create Plan workflow goes straight from prompt to draft. Nothing in the toolchain makes an engineer or agent stop and interrogate the idea first, so weak assumptions land in plans unchallenged. Decisions have no durable record — "why Dataverse here and not SQL?" is unanswerable six months later. And there is no shared environment context: every plan re-derives (or silently guesses) the org's stack, so an agent may reach for the wrong tool with nothing to challenge it against. The existing cure lives in the wrong place: /grill-with-docs — the owner's personal composition of a relentless interview plus ADR/glossary capture — sits in ~/.claude/skills/ on one machine. Engineers and project agents can't run what they don't have; "encouraged for anyone on the project" is currently impossible.

Solution

Bake the composition into planf3 itself so it ships with every project. A new workflows/discuss-plan.md carries the full interview discipline in its own text — no dependency on any personally-installed skill: one question at a time with a recommended answer, dependencies resolved first, answers taken from the codebase instead of the user wherever possible (the brownfield route), and inline capture rules — ADRs behind a three-gate test in docs/adr/, glossary terms in CONTEXT.md, deviations in STACK.md. Create Plan's documented first step becomes the discuss pass, skippable only when the requester explicitly says so; depth scales with stakes (short pass for small features, full relentless interview for new systems). Update Plan offers a grill for structural revisions only. templates/stack.md ships a generic scaffold; templates/stack.cozy.md carries the org's Microsoft stack as a copy-in seed; when neither fits, the workflow interviews the user and writes STACK.md from the answers. Everything added is context, interrogation, and records — enforcement, gating, and revert stay with git, exactly per the re-scope.

[] Phase 1: Stack Context Layer

Author the two stack templates. The entry format is the load-bearing convention of this phase: every entry is a default + when-to-use lane + escape hatch, never a bare product name. A bare inventory reads as law to an agent and suppresses exactly the trade-offs the discuss pass exists to surface; a lane with an escape hatch turns every deviation into a recordable decision instead of a violation.

1. Author the generic scaffold — templates/stack.md

  • [] Create templates/stack.md with the section skeleton — Hosting, Business Logic, Frontend, Data, Identity & Access, CI/CD, Observability, Deviations — and a short header stating living-file semantics: sessions update this file as the system evolves; it describes defaults, it does not enforce them.
  • [] Document the entry format with one fully worked example (e.g. "Azure Functions — default for event-driven/API business logic; reach for Container Apps when a process is long-running") and the Deviations rule: a deviation that clears the ADR three-gate test (hard to reverse + surprising without context + real trade-off) gets an ADR, linked from its Deviations line.

[] Phase 2: The Discuss Plan Workflow

This is the load-bearing artifact of the whole iteration. A weak interview script produces ceremony — questions engineers answer on autopilot — instead of thinking. Spend the authoring care here, and keep the file fully self-contained: it must not reference the owner's personal global skills (grilling, domain-modeling, grill-with-docs), because project machines don't have them.

1. Context load + stack seeding front-matter

  • [] Author the session-start read order: STACK.md → CONTEXT.md → docs/adr/ → specs/_index.html → (brownfield) the relevant code. Then the first-run branch: if no STACK.md exists, copy in an org seed when one is provided; else offer the generic template; else interview the user about their environment section-by-section and write STACK.md from the answers.

2. Interview core

  • [] Distill the interview discipline into the file's own text: one question at a time, each with a recommended answer and brief reasoning; prerequisite questions resolved first (call the dependency out); answer from the codebase instead of asking whenever the code can answer; challenge stack fit explicitly against STACK.md lanes ("this is customer-facing — why Power Apps?").
  • [] Write the depth rubric: short pass (goal, stack fit, edge cases — a handful of questions) for small features; full relentless interview (every branch of the decision tree) for new systems or architectural changes. New plans get the discuss pass by default — skipping requires the requester explicitly saying so. Structural revisions to existing plans get an offer; status flips and wording changes get nothing.

3. Capture rules

  • [] Inline the record disciplines: ADRs only when all three gates pass (hard to reverse + surprising without context + real trade-off), written to docs/adr/NNNN-title.md as decisions crystallize; CONTEXT.md is a glossary and nothing else (update inline as terms resolve; zero implementation detail); stack deviations update STACK.md's Deviations section; plans link ADRs inline in phase/task rationale — no CLI involvement anywhere.

4. Exit routes

  • [] Close the workflow by handing the interview's resolved decisions to the next workflow as locked inputs — greenfield → Create Plan, brownfield structural revision → Update Plan — mirroring how this very plan was authored from a collaborate session's locked decisions.

Notes

Locked decisions (collaborate session, 2026-07-04)

These six decisions were resolved in a full collaborate interview before this plan was authored. They are inputs, not open questions — do not relitigate during build.

#DecisionWhy
1Home: bake into planf3 as a self-contained workflows/discuss-plan.mdOnly things that ship with the project reach engineers and agents; personal global skills don't travel
2Entry routes: greenfield (→ Create Plan) and brownfield (→ Update Plan) sharing one interview coreBrownfield is nearly free: the interview answers from the codebase where it can instead of asking
3Trigger & intensity: discuss-by-default for new plans (explicit skip required), depth scaled to stakes; structural revisions get an offer, status flips get nothingDefault path teaches behavior without gates; mandatory ceremony on trivial work is how teams learn to route around a process
4STACK.md shape: per-repo at root; default + lane + escape hatch per entry; Deviations section; living fileA bare inventory reads as law and suppresses trade-offs; lanes turn deviations into recordable decisions
5Seeding: generic scaffold ships in templates/; the org's Microsoft stack is a separate copy-in seed; interview fallback when neither fitsKeeps planf3 a general tool (plugin flip stays viable) while the org still gets one-copy seeding
6Layout & linkage: CONTEXT.md (glossary) + docs/adr/ conventions unchanged, STACK.md beside them; plain inline links; zero plan_tool/CLI/hook/test changesStandard locations stay greppable; "it's just a hyperlink" doesn't justify new CLI surface — wiring can be added later if links prove too loose
Scope guard. This iteration is context + interrogation + records only. No enforcement, no gating, no revert mechanics — git owns those (branches/PRs, CODEOWNERS, tags, blame, CI). The compliance layer was deliberately excised in the re-scope (see back-ref); nothing here may walk that back. If a build decision seems to need enforcement, the answer is a git-layer convention, not tool machinery.
Key risk. discuss-plan.md's interview quality is the single load-bearing artifact. A weak script yields ceremony — rote questions, autopilot answers — and the whole iteration reads as process theater. That is why Phase 2 gets the authoring care and Phase 4 (dogfood + owner sign-off) gates the announcement to engineers.

Rejected alternatives

  • Vendor the personal skills (copy grilling/domain-modeling into each project) — three more things to copy per project; worsens the friction the plugin flip exists to fix.
  • Org-preloaded stack template — would make every future planf3 consumer inherit one org's Microsoft opinions as defaults.
  • ADRs under specs/ — breaks the industry-standard docs/adr/ location and drags non-plan files into index/guard/validate territory.
  • Wiring ADR links into plan metadata (meta --field refs, validate resolution) — new CLI surface + tests for what is fundamentally a hyperlink; revisit only if inline links prove too loose.
  • Always-full-depth or purely opt-in triggering — the former breeds resentment and gaming; the latter never reaches the people who most need to slow down.
